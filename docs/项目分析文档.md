## 1. 项目概述

### 1.1 项目定位

小智 AI 聊天机器人（xiaozhi-esp32）是基于乐鑫 ESP32 系列芯片的语音交互入口固件。它通过 MCP（Model Context Protocol）协议将 AI 大模型能力（Qwen、DeepSeek 等）扩展到边缘设备，实现：

- 流式 ASR + LLM + TTS 语音对话
- 离线语音唤醒（ESP-SR）
- 声纹识别（3D Speaker）
- 设备端 MCP 工具调用（音量、灯光、电机、GPIO 等）
- 云端 MCP 能力扩展（智能家居、PC 操作、邮件、搜索等）
- 支持 70+ 开源硬件、30+ 语言

### 1.2 技术栈

| 维度 | 选型 |
|------|------|
| 芯片平台 | ESP32 / ESP32-S3 / ESP32-C3 / ESP32-C5 / ESP32-C6 / ESP32-P4 |
| 开发框架 | ESP-IDF v5.4+ |
| 编程语言 | C++17（主体）+ C（部分组件）|
| 构建系统 | CMake + idf.py |
| UI 框架 | LVGL v9 + 自研 LvglDisplay 适配层 |
| 音频编解码 | OPUS（语音）/ MP3（音乐）/ OGG（提示音）|
| 通信协议 | WebSocket / MQTT + UDP（AES-CTR 加密）|
| AI 协议 | MCP（JSON-RPC 2.0，protocolVersion 2024-11-05）|
| 代码风格 | Google C++ Style（.clang-format）|

### 1.3 版本信息

- 当前版本：**v2.2.2**
- 分区表：v2（与 v1 不兼容，v1 需手动烧录升级）
- v1 稳定版：1.9.2（`git checkout v1`，维护至 2026 年 2 月）

## 3. 主流程与状态机

### 3.1 启动流程

`main/main.cc` 的 `app_main()` 执行顺序：

1. `nvs_flash_init()` — 初始化 NVS（损坏则擦除重建）
2. `Application::GetInstance()` — 获取单例
3. `app.Initialize()` — 初始化显示、音频、网络回调、MCP 工具、状态机监听器、1 秒时钟定时器；通过 `board.StartNetwork()` 异步启动网络
4. `app.Run()` — 进入永不返回的主事件循环

### 3.2 Application 单例与事件循环

`Application` 是 Meyers 单例（`application.h:46`），禁用拷贝。核心基于 FreeRTOS `EventGroup`，定义 13 个事件位（`MAIN_EVENT_SCHEDULE` 0x0001 ~ `MAIN_EVENT_STATE_CHANGED` 0x1000）。

`Run()` 中将主任务优先级提升到 10，循环 `xEventGroupWaitBits` 等待 ALL_EVENTS，按位处理：

- `MAIN_EVENT_SCHEDULE` — 取出 `main_tasks_` 队列中通过 `Schedule()` 注入的回调（线程安全派发到主任务）
- `MAIN_EVENT_CLOCK_TICK` — 每秒更新状态栏，每 10 秒打印堆统计
- `MAIN_EVENT_SEND_AUDIO` — 从 `audio_service_` 出队音频包经 `protocol_->SendAudio` 发送
- 其它 `Handle*Event()` 处理对应业务

### 3.3 设备状态机

`device_state.h` 定义 11 个状态：

| 状态 | 含义 |
|------|------|
| `Unknown` | 未知/初始 |
| `Starting` | 启动中 |
| `WifiConfiguring` | WiFi 配网模式 |
| `Idle` | 待机 |
| `Connecting` | 连接服务器中 |
| `Listening` | 听音中 |
| `Speaking` | 说话中 |
| `Upgrading` | 升级中 |
| `Activating` | 激活中 |
| `AudioTesting` | 音频自检 |
| `FatalError` | 致命错误（不可逃逸）|

`device_state_machine.cc` 用 `std::atomic<DeviceState>` 保证并发安全，`IsValidTransition()` 显式列出每个状态的合法后继（如 `Idle` 可去 `Connecting/Listening/Speaking/Activating/Upgrading/WifiConfiguring`；`Listening` 只能去 `Speaking/Idle`）。`AddStateChangeListener` 支持观察者模式。

### 3.4 ListeningMode 三种模式

定义于 `protocols/protocol.h:38`：

- `kListeningModeAutoStop` — VAD 静默自动结束（默认，AEC 关闭时）
- `kListeningModeManualStop` — 用户按键停止
- `kListeningModeRealtime` — 全双工，需 AEC 支持（设备端或服务端）

### 3.5 典型状态迁移路径

- **启动**：`Unknown → Starting → (WifiConfiguring 或 Activating) → Idle`
- **语音交互**：`Idle → Connecting → Listening → Speaking → (Listening 或 Idle)`
- **唤醒词**：`Idle` 时编码唤醒词 → 未开通道则 `Connecting` → `Schedule(ContinueWakeWordInvoke)` → 开通道后 `Listening`
- **升级**：`Idle/Activating → Upgrading → Idle/Activating`（失败回 Idle，成功 Reboot）
- **WiFi 配网态**：可经 Toggle 切到 `AudioTesting` 进行本地音频自检

### 3.6 音频通道开关流程

`ToggleChatState / StartListening / WakeWordInvoke` 三条路径：

1. 判断当前 `Idle` 且 `protocol_->IsAudioChannelOpened() == false`
2. `SetDeviceState(kConnecting)` + `Schedule(ContinueOpenAudioChannel(mode))`
3. `ContinueOpenAudioChannel` 校验状态仍为 `Connecting`，调用 `protocol_->OpenAudioChannel()`
4. 成功后 `SetListeningMode(mode)` 进入 `Listening`；失败则重新启用唤醒词检测

`protocol` 在 `InitializeProtocol()` 注册回调：`OnAudioChannelOpened` 切 `PERFORMANCE` 电源；`OnAudioChannelClosed` 非音乐播放时切回 `LOW_POWER`；`OnIncomingJson` 处理 `tts/stt/llm/mcp/system/alert` 驱动状态迁移。

### 3.7 Settings 持久化

`settings.cc` 是 NVS 薄封装：构造时 `nvs_open(ns, ...)`，析构时 dirty 则 `nvs_commit`。命名空间包括：`wifi` / `mqtt` / `websocket` / `audio` / `assets` / `display` / `backlight` / `board` / `vendor` / `led_strip` / `sparkbot` / `electron_trims` / `network` / `memo`（Waveshare 板备忘录）等。

### 3.8 Assets 资源系统

`assets.cc` 单例管理 "assets" 分区，采用策略模式：

- `LvglStrategy`（`HAVE_LVGGL=1`）：分区 mmap 到地址空间，按 `index.json` 解析资源表
- `EmoteStrategy`：用于无 LVGL 的 emote 显示方案
- `LoadSrmodelsFromIndex`：从 `index.json` 取 `srmodels` 文件调用 `srmodel_load` 加载唤醒词模型注入 `AudioService`

`Application::CheckAssetsVersion()` 在激活阶段读取 `Settings("assets").GetString("download_url")`，若有则进入 `Upgrading` 状态下载并 `Apply()`。

### 3.9 音乐播放任务

`PlayMusicFromUrl`（`application.cc:1118`）流水线：

1. 防重播：同 URL 播完 15 秒内禁止重启
2. 停止旧任务 → `AbortSpeaking` + `CloseAudioChannel` → `SetDeviceState(kIdle)` → `SetExternalPlaybackActive(true)` → 切 `PERFORMANCE` 电源
3. `xTaskCreate("music_playback", 12288, prio=3)` 创建任务
4. 任务体内：
   - `connect_id=4` HTTP 拉 LRC 歌词并解析（多时间戳排序）
   - `connect_id=3` HTTP 流式读 MP3 + `esp_audio_simple_dec` 解码
   - 声道转换（双→单或单→双）+ 采样率重采样（`esp_ae_rate_cvt`）
   - 直接 `codec->OutputData(pcm)` 绕过 AudioService 输出
   - 计算播放进度 `music_progress_ms_` / `music_total_ms_` 供 MCP 查询
   - 推进歌词行 + 进度条 UI
5. 退出条件：连续空读 30 次（约 3 秒）判 EOF、用户中断、解码失败
6. 收尾：释放资源、关闭 HTTP、`SetExternalPlaybackActive(false)`、记录 `last_played_url_` + 时间戳、切回 `LOW_POWER`

## 4. 通信协议与 MCP

### 4.1 协议层抽象

基类 `Protocol`（`main/protocols/protocol.h`）定义纯虚接口：

- `Start()` — 启动协议客户端
- `OpenAudioChannel()` / `CloseAudioChannel()` — 打开/关闭会话级音频通道
- `IsAudioChannelOpened()` — 通道是否可用
- `SendAudio(AudioStreamPacket)` — 发送一帧音频
- `SendText(text)`（protected 纯虚）— 派生类实现具体链路

统一回调入口：`OnIncomingJson` / `OnIncomingAudio` / `OnAudioChannelOpened/Closed` / `OnNetworkError` / `OnConnected/Disconnected`，由 `Application` 注册消费。

基类内置设备→服务器标准消息封装：`SendWakeWordDetected` / `SendStartListening(mode)` / `SendStopListening` / `SendAbortSpeaking(reason)` / `SendMcpMessage(payload)`，统一拼装带 `session_id` 与 `type` 的 JSON 文本。

数据结构：
- `AudioStreamPacket` — 采样率/帧长/时间戳/负载
- `BinaryProtocol2` — 带时间戳二进制头（用于服务端 AEC）
- `BinaryProtocol3` — 精简头
- 内置 120 秒空闲超时 `IsTimeout()`

### 4.2 WebSocket vs MQTT 实现

| 维度 | WebSocket | MQTT + UDP |
|------|-----------|------------|
| 通道模型 | 单一 WebSocket 双向 | MQTT 控制 + UDP 音频 |
| 连接时机 | `OpenAudioChannel()` 才连 | `Start()` 立即建立 MQTT |
| 音频传输 | 二进制帧（version 1/2/3）| AES-128-CTR 加密 UDP |
| 重连机制 | 由 OpenAudioChannel 触发 | 60 秒重连定时器 |
| 配置命名空间 | `Settings("websocket")` | `Settings("mqtt")` |
| 关闭 | 不发 goodbye | 发 goodbye + 复位 UDP |

**MQTT+UDP 加密细节**：`OpenAudioChannel` 通过 MQTT 发 `hello`（`transport:"udp"`），服务端回包含 `udp.server/port/key/nonce`，设备 `mbedtls_aes_setkey_enc` 生成 AES-128-CTR 上下文。发送时 nonce + timestamp + `local_sequence_` 拼装后 CTR 加密；接收时校验 `remote_sequence_` 防重放。

**切换机制**：两者都通过基类指针 `Protocol*` 被 `Application` 持有，具体实例由板级 `Board` 工厂根据编译配置创建。`Ota::CheckVersion()` 解析服务器返回的 `mqtt` / `websocket` JSON 段并写入对应 `Settings`，支持服务端下发切换。

### 4.3 MCP 设备端实现

`McpServer`（`main/mcp_server.cc`）单例，承担"设备作为 MCP Server"角色。MCP 消息承载于基础协议文本帧中，外层由 `Protocol::SendMcpMessage` 包装为 `{"session_id","type":"mcp","payload":<JSON-RPC 2.0>}`，`payload` 内部遵循 JSON-RPC 2.0，`protocolVersion` 为 `2024-11-05`。

**支持 method**：

- `initialize` — 解析 `capabilities.vision`（含 `url/token`）注入 Camera；回 `serverInfo`（`BOARD_NAME` + 固件版本）
- `tools/list` — 支持 `cursor` 分页（单包 8000 字节上限）和 `withUserTools` 布尔过滤；`user_only` 工具通过 `annotations.audience=["user"]` 标注仅对用户可见
- `tools/call` — 根据 `name` 查表，按 `Property` 类型（bool/int/string，含 min/max 校验）解析 `arguments`，再 `Application::Schedule` 投递到主线程执行，避免抢音频线程

**内置工具**（`AddCommonTools`）：`self.get_device_status` / `self.audio_speaker.set_volume` / `self.music.play_url` / `self.screen.set_brightness` / `self.screen.set_theme` / `self.camera.take_photo`

**用户级工具**（`AddUserOnlyTools`）：`self.get_system_info` / `self.reboot` / `self.upgrade_firmware` / `self.screen.get_info` / `self.screen.snapshot` / `self.screen.preview_image` / `self.assets.set_download_url`

**板级扩展**：通过 `InitializeTools` 注册自定义工具（如 `self.dog.forward`、`self.light.set_rgb`、`self.weather.update` 等）。

返回值 `ReturnValue` 支持 bool/int/string/cJSON*/ImageContent*，统一封装为 `{"content":[{"type":"text"|"image","text"|...}],"isError":false}`。设备亦可经 `Application::SendMcpMessage` 主动发 notification。

### 4.4 OTA 升级流程

`Ota`（`main/ota.cc`）通过 HTTP 与服务器交互：

1. `CheckVersion()` — 携带 `SystemInfo` JSON 调用 `ota_url`，响应含 `firmware{version,url,force}` / `mqtt` / `websocket` / `server_time` / `activation` 段。版本比较按 `.` 分段逐位比对，`force==1` 强制升级
2. `StartUpgrade(callback)` → `Upgrade(url)` — `esp_ota_get_next_update_partition` 选分区，4KB 缓冲流式写入。先校验镜像头再 `esp_ota_begin(OTA_WITH_SEQUENTIAL_WRITES)`，完成后 `esp_ota_end` + `esp_ota_set_boot_partition`
3. `MarkCurrentVersionValid()` — 非 factory 分区把 `ESP_OTA_IMG_PENDING_VERIFY` 置为 valid 防回滚

### 4.5 设备激活流程

`Ota::Activate()` 在 `CheckVersion` 收到 `activation.challenge` 时触发：

- **v2 激活**（efuse 有 `serial_number`）：`esp_hmac_calculate(HMAC_KEY0, challenge)` 生成 SHA-256 HMAC，组装 `{algorithm:"hmac-sha256", serial_number, challenge, hmac}`
- **v1 激活**（无 serial_number）：返回 `{}`

POST 到 `<ota_url>/activate`，HTTP 头携带 `Activation-Version: 1|2`、`Device-Id`、`Client-Id`、`Serial-Number`、`User-Agent`、`Accept-Language`。响应 `202` 待激活（`ESP_ERR_TIMEOUT`），`200` 成功。

### 4.6 关键 JSON 字段

| 顶层字段 | 含义 |
|----------|------|
| `session_id` | 会话 ID |
| `type` | hello/listen/abort/tts/stt/llm/mcp/system/goodbye/custom |
| `transport` | websocket/udp |

| 消息类型 | 关键字段 |
|----------|----------|
| `hello` | `version` / `features{mcp,aec}` / `audio_params{format,sample_rate,channels,frame_duration}` / `udp{server,port,key,nonce}` |
| `listen` | `state`(start/stop/detect) / `mode`(auto/manual/realtime) / `text` |
| `tts/stt/llm` | `state`(start/stop/sentence_start) / `text` / `emotion` |
| `mcp` | `payload` 内为 JSON-RPC 2.0 |
| `system` | `command`(reboot 等) |

## 5. 音频子系统

### 5.1 整体架构

音频子系统以 `AudioService` 为中央调度器，采用三层抽象：

- 硬件编解码器层（`AudioCodec`）
- 音频前处理层（`AudioProcessor`）
- 唤醒词层（`WakeWord`）

通过 OPUS 编解码实现与服务器之间的低延迟语音流传输。

### 5.2 AudioService 任务调度

`AudioService` 维护 **三条 FreeRTOS 任务** 和 **五个数据队列**，形成双工音频流水线：

| 任务 | 优先级 | 核心 | 职责 |
|------|--------|------|------|
| `AudioInputTask` | 8 | core 0 | 通过事件组位切换三种工作模式（唤醒词/处理器/测试），按 `GetFeedSize()` 读取 PCM 喂给唤醒词或处理器 |
| `AudioOutputTask` | 4 | - | 阻塞等待 `audio_playback_queue_`，从队列取 PCM 调 `codec_->OutputData` 写入 I2S |
| `OpusCodecTask` | 2（栈 24KB） | - | 单任务同时承担编码与解码。条件变量在"encode 队列非空且 send 队列未满"或"decode 队列非空且 playback 队列未满"时唤醒 |

**队列容量**：编码/播放任务队列各 2，解码/发送包队列按 `2400ms / 60ms = 40` 个，溢出时丢弃并计数（`decode_drop_total_`）。

**省电机制**：`audio_power_timer_` 每秒检查 `last_input_time_/last_output_time_`，15 秒无活动则关闭 codec 输入/输出，外部播放期间强制保持输出开启（`SetExternalPlaybackActive`）。

### 5.3 AudioCodec 抽象与实现

基类 `AudioCodec` 封装 I2S 双通道（`tx_handle_/rx_handle_`）、音量、增益、输入输出使能；定义纯虚 `Read/Write`。

| 实现 | 特点 |
|------|------|
| **ES8311** | 单 codec 全双工，`input_channels_=1`，`input_reference_=false`（无硬件 AEC 参考）|
| **ES8388/ES8374/ES8389** | 双 dev 句柄（`output_dev_/input_dev_`），支持 `input_reference` 开启参考通道用于 AEC |
| **BOX** | ES8311（输出）+ ES7210（输入）组合，独立 in/out ctrl_if 与 codec_if，多通道输入 |
| **NoAudioCodec** | 无外部 codec 芯片，直接用 I2S STD/PDM。派生 Duplex/Simplex/SimplexPdm 三种 |

ES8311 通过 `UpdateDeviceState()` 在首次使能时才 `esp_codec_dev_open`，并控制 PA 引脚电平（支持 `pa_inverted_`）。

### 5.4 AudioProcessor（AFE 前处理）

`AfeAudioProcessor` 基于 ESP-ADF AFE，配置 `AFE_TYPE_VC` + `AEC_MODE_VOIP_HIGH_PERF`：

- **降噪 NS** — 优先加载 NSNet 模型，`AFE_NS_MODE_NET`；无模型则 `ns_init=false`
- **AEC** — 默认 `aec_init=false`；若编译 `CONFIG_USE_DEVICE_AEC` 则启用硬件参考路 AEC 并关闭 VAD
- **VAD** — `VAD_MODE_0` + 可选 VADNet 模型，状态变化经 `OnVadStateChange` 回调上报 `voice_detected_`
- **任务流** — 独立 `audio_communication` 任务调 `afe_iface_->fetch_with_delay`，按 `frame_samples_`（60ms×16kHz=960 样本）切片回调输出

`NoAudioProcessor` 为透传回退实现。

### 5.5 WakeWord 三种实现

通过 `SetModelsList` 按模型前缀选择（`audio_service.cc:819`）：

| 实现 | 平台 | 模型 | 特点 |
|------|------|------|------|
| `AfeWakeWord` | S3/P4 | AFE_TYPE_SR + Wakenet | 维护 2 秒环形缓冲，独立 OPUS 编码任务供声纹识别 |
| `CustomWakeWord` | S3/P4 | Multinet | 支持自定义命令词，配置 `commands_` 列表与 `language_/threshold_/duration_` |
| `EspWakeWord` | C3/C5/C6/ESP32 | Wakenet | 仅 `esp_wn_iface_t`，最轻量 |

AfeWakeWord 检测到 `WAKENET_DETECTED` 后停止检测并回调；维护 `wake_word_pcm_` 环形缓冲（约 2 秒数据），`EncodeWakeWordData()` 在静态任务（PSRAM 栈）中独立 OPUS 编码，经 `wake_word_opus_` 队列 + 条件变量供上层 `PopWakeWordPacket` 取出上传，用于声纹识别。

### 5.6 OPUS 编解码配置

- 采样率：16kHz 单声道 16bit
- 帧长：60ms
- 比特率：`BITRATE_AUTO`
- 复杂度：`complexity=0`（最低）
- VBR + DTX（静音抑制）：启用
- 解码：按服务器上报的 `sample_rate/frame_duration` 动态重建 decoder（`SetDecodeSampleRate`）

**重采样**：`input_resampler_` 将 codec 输入采样率转 16kHz 喂 AFE；`output_resampler_` 将解码 PCM 转 codec 输出采样率。模式切换时调 `esp_ae_rate_cvt_reset` 清缓存防溢出。

### 5.7 完整数据流

**上行（用户→服务器）**：
```
Mic → codec->InputData → (input_resampler) → 16kHz PCM → AudioProcessor.Feed
    → AFE fetch → OPUS encode → audio_send_queue → PopPacketFromSendQueue → 协议层
```

**下行（服务器→用户）**：
```
协议层 → PushPacketToDecodeQueue → OPUS decode → (output_resampler)
    → audio_playback_queue → codec->OutputData → Speaker
```

**唤醒词上行（声纹）**：
```
Mic → AfeWakeWord.Feed → 检测命中 → 缓存 2s PCM → EncodeWakeWordData
    → OPUS 包队列 → PopWakeWordPacket → 协议层
```

**Server AEC**：若启用 `CONFIG_USE_SERVER_AEC`，`AudioOutputTask` 播放时把 `task->timestamp` 压入 `timestamp_queue_`，编码上行帧时取出对应时间戳随包发送，供服务器端做回声对齐。

**PlaySound**（`audio_service.cc:655`）— 直接解析内嵌 OGG 容器，提取 OpusHead 采样率与 Opus 音频包，绕过编码直接灌入解码队列，用于提示音播放。

## 7. Waveshare ESP32-S3-RLCD-4.2 板子详解

### 7.1 硬件定位

`main/boards/waveshare-s3-rlcd-4.2/` 是 **400x300 1-bit 单色反射式 LCD（RLCD）+ ESP32-S3 + SD 卡 + I²C 传感器集群** 的板子。它是该项目中**唯一使用 1-bit 单色 RLCD** 的板子。

### 7.2 引脚配置（`config.h`）

| 功能 | 引脚 |
|------|------|
| I2C 主总线（共享 ES8311/ES7210/SHTC3/PCF85063）| SDA=13 / SCL=14 |
| LCD SPI3 | MOSI=12 / SCK=11 / DC=5 / CS=40 / RST=41 / TE=6 |
| LCD 尺寸 | 400x300 |
| USER 按钮 | GPIO18 |
| 电池 ADC | ADC1_CH3 |
| 音频 PA | GPIO46 |

### 7.3 自研 RLCD 驱动

`rlcd_driver.h/cc` 实现自研 1-bit 单色驱动层：

- 1-bit 单色缓冲区
- 提供 `RLCD_Init/ColorClear/SetPixel/Display/SetContrast`
- 内部用 `PixelIndexLUT[300]` 与 `PixelBitLUT[300]` 查找表加速 RGB565→1-bit 转换
- 支持竖屏/横屏两种 LUT

### 7.4 CustomLcdDisplay 自定义显示

`custom_lcd_display.h` 继承 `LcdDisplay`，三页面模式：

| 模式 | 内容 |
|------|------|
| `MODE_WEATHER` | 时钟 + 日历 + 天气 + AI 对话 + 备忘录卡片 |
| `MODE_MUSIC` | 音乐播放器（进度条 + 歌词三行）|
| `MODE_POMODORO` | 番茄钟倒计时 |

关键实现：
- 自定义 `Lvgl_flush_cb` 把 LVGL 的 RGB565 转 1-bit 刷到 RLCD
- 省电策略：5 分钟无活动 → 刷新从 1 秒降到 5 秒
- 重写 `SetTheme` 为空避免单色屏崩溃

### 7.5 UI 子模块

- `weather_ui.cc` / `music_ui.cc` / `pomodoro_ui.cc` — 三套页面 UI 布局
- `data_update_task.cc` — 后台 FreeRTOS 任务，周期性更新时间/天气/传感器/电池/WiFi/AI 状态/番茄钟
- `managers/SensorManager` — SHTC3 温湿度 + PCF85063 RTC + NTP 同步
- `managers/WeatherManager` — 支持 `updateFromExternal` 由 AI MCP 回写
- `managers/SdcardManager` — SDMMC 模式，白噪音源
- `managers/PomodoroManager` — 专注倒计时

### 7.6 板级初始化与 MCP 工具

`waveshare-s3-rlcd-4.2.cc` 继承 **WifiBoard**（注意：不是 DualNetworkBoard），构造函数顺序：

```
InitializeI2c → InitializeSensors → InitializeSdcard
→ InitializeButtons → InitializeTools → InitializeLcdDisplay
```

注册的 MCP 工具：

- `self.system.info`
- `self.weather.update`
- `self.disp.network` / `self.disp.switch`
- `self.pomodoro.start` / `stop` / `status` / `pause`
- `self.memo.add` / `list` / `done` / `clear`

### 7.7 电池读取自研实现

- `BatterygetVoltage` — 用 ADC1_CH3 + `adc_cali_curve_fitting` 校准，电压×3（分压比）

### 7.8 音频配置

使用 `BoxAudioCodec`（ES8311 输出 + ES7210 输入，24kHz 双向，PA=GPIO46）。

### 7.9 USER 按钮交互

- 单击：切换页面
- 双击：刷新数据
- 长按：显示系统信息（用「鱼咬尾」双份内容 + LVGL 动画无缝循环滚动）

## 8. 关键技术点与扩展点

### 8.1 关键技术点

1. **多板适配架构**：通过 `DECLARE_BOARD` 宏 + `create_board()` 工厂 + Kconfig `BOARD_TYPE` 选择，单一固件源码支持 70+ 板子，编译时按需包含板子目录
2. **协议层抽象**：`Protocol` 基类 + WebSocket/MQTT 双实现，可由服务端 OTA 响应下发切换，支持热迁移
3. **MCP 设备端工具**：JSON-RPC 2.0 标准协议，板级通过 `InitializeTools` 注册自定义工具，让大模型可直接调用硬件能力
4. **双工音频流水线**：三任务五队列设计，OPUS 编解码单任务串行避免双核竞争，60ms 帧长平衡延迟与吞吐
5. **AEC 三模式**：关闭 / 设备端 AEC（硬件参考路）/ 服务端 AEC（时间戳对齐），适配不同硬件能力
6. **状态机严格性**：`IsValidTransition` 显式枚举合法迁移，`FatalError` 不可逃逸，避免非法状态跳转
7. **资源分区管理**：assets 分区 + mmap + `index.json` 资源表，支持运行时下载更新与版本校验
8. **v2 激活机制**：efuse `serial_number` + HMAC-SHA256 挑战响应，防克隆
9. **多语言支持**：30+ 语言，编译时按 `LANG_DIR` 选择，缺失音频自动回退 en-US
10. **声纹识别数据通道**：唤醒词检测后单独 OPUS 编码任务，2 秒 PCM 环形缓冲，专供 3D Speaker 声纹识别

### 8.2 扩展点

| 扩展方向 | 入口 |
|----------|------|
| 添加新板子 | `main/boards/<new-board>/` + Kconfig `BOARD_TYPE_*` + CMakeLists.txt 映射 |
| 添加自定义唤醒词 | `CONFIG_CUSTOM_WAKE_WORD` + `custom_wake_word.cc` |
| 添加 MCP 工具 | 板级 `InitializeTools` 中 `AddTool` |
| 添加新音频 codec | `main/audio/codecs/` + 继承 `AudioCodec` |
| 添加新显示类型 | `main/display/` + 继承 `Display` 或 `LvglDisplay` |
| 添加新协议 | `main/protocols/` + 继承 `Protocol` |
| 添加新语言 | `main/assets/locales/<lang>/` + Kconfig `LANGUAGE_*` |
| 切换通信协议 | OTA 响应 `mqtt`/`websocket` 字段下发，自动写入 Settings |

### 8.3 性能与限制

- **OPUS 复杂度 0** — 最低 CPU 占用，但音质略损
- **音频队列 40 包上限** — 2400ms 缓冲，溢出丢弃
- **MCP 单包 8000 字节** — 超过分页 `cursor`
- **唤醒词检测需要 PSRAM** — S3/P4 + SPIRAM 才能用 AFE/Custom
- **设备端 AEC 限制** — 需要干净输出参考路与物理声学隔离，仅特定板子支持

### 8.4 开发注意事项

1. 编译前需 ESP-IDF v5.4+，Linux 编译速度优于 Windows
2. 板子目录支持 `managers/` / `assets/` 子目录，CMake 递归 GLOB
3. `WHOLE_ARCHIVE` 选项确保 `DECLARE_BOARD` 链接正确
4. 字体通过 `xiaozhi-fonts` 组件动态查找，`BUILTIN_TEXT_FONT` / `BUILTIN_ICON_FONT` 编译期决定
5. ESP32（非 S3）会排除部分 codec/display/nt26/ml307/dual 文件避免编译错误
6. ESP-SR 模型路径通过 `find_component_by_pattern` 动态查找 `espressif__esp-sr` 组件
